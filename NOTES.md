## Sheet layout (pages as the Permanent Character Record, our own look; note: the look is now black and white, Jost, light and dark themes, see the CSS header)
Identity block on every page, then tabs: 1 Abilities (six ability rows with every table figure, saves, movement by encumbrance, vision and resistances, psionics, languages) / 2 Combat (weapons of proficiency, non-proficiency penalty, to-hit AC 10 to -10 for melee and missile, combat adjustments, weapon table with damage S-M/L, speed, space/ranges and weapon adjustment vs armour type 10 to 2, hit points and hit dice, hp per level, scarring and maiming) / 3 Skills and look (thief/assassin/monk skills base+race+dex+other, description) / 4 Equipment (price-list picker, custom items, live encumbrance and AC, coins) / 5 Spells (spells per day from derive, known and memorised per level, spell-name suggestions from the treasure engine's PHB lists) / 6 Notes / 7 Retainers (henchmen and hirelings, see below). No TSR logo, wordmark, art or border is used.

## Stored data
Key `io.github.solid-state-games.1e-toolkit/sheet` on the token's item metadata (owner key `.../owner`). Inputs only (race, sex, classes, levels, six final scores, strength exception, alignment, hp, xp, hp per level, proficiencies, gear as `[name, qty]` or `[name, qty, lb, ac]` for custom items, coins, spells known and memorised, languages, description, injuries, notes, conditions, thief "other" adjustments). Everything else is derived by `Rules.derive`. Every field is length-capped in `sanitize`, so the worst case is bounded: test (a) fills every field to its cap (120 gear lines, 3000-char notes, 160 spells, etc.) and gets 10,539 bytes; 500 random legal characters peak at about 1.2 kB. The sheet refuses to save at 16,000 bytes and shows a meter.

## Private sheets (TB, 2026-11-12: "important in 1e")
- A sheet's owner is the player the GM assigned (Characters tab, Assign), else whoever placed the token.
- Only the owner and the GM can open it: the right-click item refuses, the player's Characters list omits it,
  and the sheet page shows "belongs to another player" with no data rendered or exportable.
- Limit: Owlbear sends every scene item, metadata included, to every browser in the room. A player who opens
  browser dev tools could read another sheet's raw data. Owlbear has no private per-player storage, so true
  secrecy would need storing the sheet outside the room (e.g. the player's own browser plus export to the GM).

## Permissions design
- Open: GM any character token; player tokens they created, or tokens the GM assigned (`owner` metadata = player id). The context menu item shows on every character-layer token (OBR's filter cannot test ownership); the click handler refuses with a notice if it is not theirs.
- Write: GM always. Player if `createdUserId == me` (OBR lets players update items they created), or if assigned AND the room grants `CHARACTER_UPDATE` (checked with `player.hasPermission`). Otherwise the sheet opens read only (inputs disabled, banner, export still works). Every save is also try/caught, so an OBR refusal shows "NOT SAVED: reason".
- Assign (GM): writes `owner` and then attempts `createdUserId = playerId` so the player can save. `createdUserId` is a writable field in the SDK types, but I could not confirm real OBR lets a GM change it. If it refuses, the player gets read only (or the room can grant CHARACTER_UPDATE). **TD/TB: verify in a real room.**
- GM tabs are not rendered at all for players (no DOM nodes); GM tabs read no private data, so there is nothing to leak.

## Places and retainers (added 2026-11-12)
**Equipment tab, items left elsewhere.** `lp` = places, `[name, pp, gp, ep, sp, cp]` (max 10, name 30, coins 99,999 each). An inventory entry that is in place n gets a trailing string `"n"` (1-based); no string = Carried, so old saves load unchanged. Only Carried items and `co` go to `toChar`/`hydrate`, so load, movement and AC ignore the rest. The table is grouped by place with a "Move to" box and optional count (splits a stack, merges with the same plain item); removing a place with items or coins shows an inline confirm and moves them to Carried. Coins per place with a gp worth (PHB p.35 values).
**Tab 7 Retainers.** `hn` henchmen (max 15, PHB p.13): `[name, race, class, level, hp, ac, share, pay gp/month, token id, notes, m]`, `m` = one choice per loyalty category (0 = none) then special penalty and special bonus, trailing zeros dropped. `hr` hirelings (max 20): `[kind 0 soldier / 1 expert, index, number, serjeants or level or agreed gp, note]`; soldier index into `SheetRules.SOLDIERS` (append only; pay from `QPRules.MERC`, DMG p.29), expert index into `SheetRules.EXPERTS`. Nothing derived is stored (loyalty total, costs, max henchmen are computed). `lib/quickparty_rules.js` is now loaded by index.html for MERC.
- Henchmen: Charisma maximum and loyalty base from `Rules.derive` (PHB p.13; own-race figure for dwarf and half-orc PHB p.16-17), warning when over. Loyalty = 50 (DMG p.36) + Charisma adjustment + one choice from each DMG p.36-37 category + liege alignment (automatic from the sheet's alignment, DMG p.37) + one special penalty and one special bonus + this-check situation counts (not saved). "Check loyalty" rolls d100 (00 = 100); the check fails if the total is less than the roll (DMG p.36), and the typical failure result for the chosen situation is shown. Bands (None, Disloyal, Little, Fair, Loyal, Fanatical) DMG p.36. Level note when a henchman is at or above the PC's highest level (DMG p.34, p.36). "Linked token": a character-layer token; the Open button shows only if the viewer may open that sheet (GM, or the owner under the private-sheet rule).
- Hirelings: soldiers (pay DMG p.29, serjeants 10 times the rate DMG p.31), experts with printed costs (DMG p.29-34); per-level costs (captain, lieutenant, steward/castellan, ship officers) take a level; ranges (sage 200-1,200 twice, spy 100-10,000+) take the agreed figure (low end counts until entered); the spy is per assignment so not in the month. Monthly total = henchmen pay + hirelings. **Pay a month** asks to confirm, then spends gold first from the chosen place (change in gp, sp, cp); refuses if the coins are short.
- Size: all caps in `LIM` and shown on the page. Test (e) fills the old maximal sheet plus 120 gear lines all in places, 10 places, 15 henchmen, 20 hirelings: 15,567 B. A caster with 160 known spells at their longest can already pass 16 kB without the new fields (pre-existing; the save is refused with a message).
- Private sheets still hold: retainers are inside the sheet, so a non-owner gets only the "belongs to another player" notice (browser test seeds another player's sheet with a henchman and checks the page text).

## Interpretations (TB to confirm)
1. **Missile adj** is shown as the Dexterity reaction/attacking figure (PHB p.11 Table I gives one adjustment for both); the missile to-hit row uses it, the melee row uses Strength hit adj (PHB p.9).
2. **Strength damage** is added to melee weapon damage in the weapon table only; thrown weapons are not given it (PHB p.9 does not say, so literal reading).
3. **Weapon adjustment columns** use the combat_rules table keyed by armour type 10 to 2 (PHB p.38); "Hit adj" in that table is Str (melee) or Dex (missile), not the weapon adjustment, which is the 10-to-2 columns.
4. **Coins:** 1 pp = 5 gp, 1 ep = 1/2 gp, 20 sp = 1 gp, 200 cp = 1 gp (PHB p.35); every coin weighs one gp of weight (the rules_1e convention, listed there as an interpretation), not "by value".
5. **Experience** is divided equally between classes (PHB p.14-17) and shown as "next level at" per class plus a note when the xp already reaches a higher level; the sheet never changes levels for you.
6. **Elf +1 to hit** (bows other than crossbows, short and long sword, PHB p.16) is listed as a trait but not added into the to-hit rows (it depends on the weapon; players put it in combat adjustments).
7. **Racial detection abilities** (dwarf, gnome, halfling slope/depth/etc.; elf and half-elf secret doors; elf 90% and half-elf 30% sleep/charm resistance) are typed into `RACE_TRAITS` from PHB p.16-17, read across two-column text. Please check pages and figures.
8. **Times raised (max)** shows the lib's `maxRaises` (= Constitution score, PHB p.12 resurrection note).
9. **Magic attack adj** is the Wisdom "magic defence" figure from rules_1e (PHB p.11).
10. **Saving throw table page** cited as DMG p.79 (as rules_1e does); the five save columns carry the DMG names.
11. **Weapon proficiency**: the pick list is limited to weapons the class may use (PHB p.19) that have a combat-table row; the count is advisory (initial slots shown), not enforced. Dagger/spear/club/hammer/hand axe proficiency lists both melee and missile rows.
12. **Shield and armour magic bonuses**, magic-item effects and the elf/dwarf/etc. to-hit bonuses are not computed (the libs carry none); the Combat page has free condition lines.
13. **Bard** (Unearthed Arcana) is out of scope: no bard class in the libs; the Skills page shows skills for thief, assassin and monk.
14. **Psionics** are free text: the libs hold no psionics tables (DMG Appendix I).
15. Class pick list per race is `RACES[race].limits` singles plus `multi` combos; an existing combination that becomes illegal after a race change is kept and flagged in a banner, not blocked.

## Interpretations for places and retainers (TB to confirm)
1. **Loyalty compare:** DMG p.36 says the check fails "if the total is less than the number shown on the dice", so total equal to the roll holds. d100 with 00 = 100; a total over 100 (Fanatical) therefore never fails.
2. **Special considerations (DMG p.37)** "Apply only one penalty and one bonus maximum, whichever of either category is the higher": the sheet offers one penalty select and one bonus select, so the player picks the higher.
3. **General treatment note (DMG p.36)** (cruel and domineering minus only when the liege is absent; near and in power, minuses become pluses, else 0% fear) is shown as a hint, not automated: the player picks the figure that applies.
4. **Alignment of liege (DMG p.37)** is taken from the sheet's own alignment automatically. The "places removed" rows and both racial-preference columns are chosen by hand ("associated group" read as the other henchmen and hirelings).
5. **Situation modifiers (DMG p.37)** are per-check counts and not stored.
6. **Henchman level note:** the DMG gives no single "lower level" sentence; the note cites DMG p.34 (new henchmen are 1st level, a PC over 6th may draw 2nd, over 11th 3rd) and p.36 (an NPC more than two levels above the PC accepts only associate status), and shows when a henchman's level is at or above the PC's highest class level. DMG p.228 calls a henchman "a low-level non-player character".
7. **Henchman pay:** DMG p.25 lists "maintenance of henchmen 100 g.p. per level per month, in addition to all treasure shares" as a campaign expense the DM deducts; the sheet offers it as a button filling the pay field, which the player may override. It is included in the monthly total.
8. **Serjeants** are counted as part of a soldier line ("of which serjeants" at 10 times the rate, DMG p.31); captains and lieutenants are expert lines at 100 gp per level (DMG p.30-31).
9. **Starred experts** (armorer, engineer-architect, jeweler-gemcutter, weapon maker): the extra 10% of item cost per job (DMG p.29 note) is a hint only. Demi-human multipliers (DMG p.30) and short-term artillerist increases (p.30-31) are hints; enter the agreed figure.
10. **Sage:** support and salary and research grants are two lines, each 200-1,200 gp a month (DMG p.33); the 20,000 gp initial material expenditure is not a monthly cost. Short-term sage fees (100 gp a day) are not modelled.
11. **Spy** is 100 to 10,000+ gp per assignment, paid by instalments (DMG p.34); kept out of the monthly total.
12. **Pay a month** spends gold first then silver, copper, electrum, platinum, and gives change in gp, sp, cp; the book gives no rule for making change.
13. **Items at a place** keep their weight but are not counted at all in load; armour left there gives no AC and does not cap movement (PHB p.36, p.101 read literally: armour worn).

14. **Command chain (DMG p.30-31), Retainers tab:** a command check shows regular soldiers vs serjeants (warn under 1 per 10, read as ceil(regular/10)), and soldiers vs lieutenant (decades per level) plus captain (scores per level) capacity when over 10 regular soldiers; a captain is expected over 20 soldiers (DMG p.30 table footnote). Officers are expert lines at 100 gp a level and are in the monthly total. Fighter level ranges (lieutenant 2nd-3rd, captain 5th-8th) are shown, not enforced. Serjeants within capacity is read literally as "up to 10 each".
15. **Ranger (PHB p.24):** a ranger below 8th level gets a warning banner on Retainers (not a block, so old saves and DM-approved play still work).
16. **Command limit (TB ruling, 2026-11-12, built on DMG p.30-31: a serjeant is a 1st-level fighter and commands up to 10 soldiers):** a PC of the fighter group (fighter, paladin, ranger, or any multi-class including one) commands up to 10 regular soldiers directly; any other PC up to 5. Above that, soldiers need serjeants (10 each, read as ceil((regular - limit) / 10), replacing the old 1 per 10 rule), then lieutenants and captains as in item 14. Held in `SheetRules.MERC_CAP_BY_CLASS` (others `MERC_CAP_OTHER` = 5) and `directCap`; the command check prints "TB ruling from DMG p.30-31"; warns, never blocks.
17. **Assassin (PHB p.30, read from the page):** no hirelings until 4th level; from 4th lower-level assassins only; from 8th thieves too; from 12th any class; only neutral or evil characters will serve; henchmen number by Charisma. A banner on Retainers (like the ranger rule) shows the current band and flags hirelings listed below 4th level. Literal reading of "neutral or evil": true neutral and the three evil alignments pass; lawful neutral, chaotic neutral and neutral good are flagged (TB to confirm). Hireling classes are not tracked, so "lower level assassins only" is a notice, not a check.
18. **Loyalty is GM only (TB, 2026-11-12):** a player sees no loyalty anywhere on the sheet (Abilities loyalty base, henchman details, Charisma base line, check, results). The GM (TK.role GM) sees and edits it in the henchman drawer and rolls the check. Stored as before (table-level privacy is enough). The player's Export JSON and Copy JSON blank the loyalty choices; a player import keeps a same-named henchman's existing choices (so a GM's entries survive) and otherwise clears them. The GM export is complete.

### Interpretations (TB to confirm)
1. Ammunition = price-list ammunition (arrows, bolts, sling bullets and stones) plus darts and javelins, carried only. Count = quantity x pack size in the name ("Arrow, normal (12)" x 2 = 24); minus fires one, plus picks one up but never above what is carried; the Full sheet quantity is the carried total, Simple tracks what is spent. Not an RAW rule (the books give no ammunition tally); bow and launcher pairing is not checked.
2. Spell ticks follow memorised order; two copies of one spell are two chips. Rest (a full night's rest, PHB p.40 memorisation) clears all ticks; no confirm button.
3. "Weapons in hand" = the proficient weapons listed on the sheet (no wielded flag exists).
4. HP full is editable in Simple as well as HP now.
5. Worn = any carried item with an AC value or a shield; everything else carried (not ammunition) is gear.
6. The situation-now modifiers are one shared set for all henchmen in a check (per-henchman sets were dropped); the typical-situation pick is shared too.


## Creating a character: Blank / Wizard / Random PC (2026-11-12)
**Flow.** A token with no sheet no longer gets an empty sheet saved on open: the sheet page shows three choices (the hub's "Create" and the right-click item both open it). Only for tokens the user may edit (private-sheet rules unchanged; a non-owner still sees "belongs to another player"). Gear, Settings, New character asks first when a sheet exists ("Replace it" / "Keep it"). Nothing is saved until Blank, Use (Random) or the wizard's Finish.
- **Blank sheet:** as before (fighter 1, name from the token).
- **Wizard:** `wizard/index.html?embed=1&theme=` in an iframe inside the sheet modal. The message is accepted only if `event.source` is that iframe and `event.origin` is our own origin. `SheetRules.fromCreator(char, tokenName)` converts it.
- **Random PC:** level choice (1, 2-4, 5-8, 9-12; a level is picked in the band) and ability method I to IV (default I), `QPRules.genPCParty({count:1, levelRange, method, alignMode:'any'}).chars[0]` (wraps `genPC`, and adds the DMG App. P magic items and equipment record), `SheetRules.fromQuickParty(rec, tokenName)`, `previewLine` (race, class, level, alignment, six scores, HP, AC), Re-roll, Use this character, Back.
- **Files:** `js/sheet_rules.js` (fromCreator, fromQuickParty, previewLine, qpSpells, coinsFromCP), `js/sheet_ui.js` (paintCreate, createAct, adopt, message listener), `css/toolkit.css`, `wizard/` (copies), `test/toolkit.test.js` section (h), `test/browser_run.js`.

### 2. Magic items and armour class (DMG p.28, 81, 124, 125-169, 164-165)
**Worn marks.** Carried items only (armour left at a place is never worn: PHB p.36, existing rule 13). Stored as one trailing string on the inventory row: `"w"` worn, `"x"` not worn, `"wN"` Defender holding N for AC. Only exceptions to the item's default are stored (ordinary armour and shield default worn, everything else not worn), so old saves load unchanged and typical sheets cost nothing. A mark on a plain item is dropped; moving an item to a place drops it. A legacy custom row with a stored AC (for example an old Quick Party "Chain Mail +1" row with AC 4) is read by its name now, and being magic it starts not worn: tick it. Other custom rows with an AC stay "ordinary armour" and stay worn.
**Recognition.** By name (typed or from the picker on the Equipment page): `Chain Mail +1`, `Plate Mail of Etherealness`, `Plate Mail of Vulnerability -2`, `Shield +2`, `Shield, large, +1, +4 vs. missiles`, `Shield -1, missile attractor`, `Ring of Protection +2` (and the +4/+6 forms), `Bracers of Defense AC 4` (or `, AC 4`), `Cloak of Protection +3`, `Cloak of Displacement`, `Boots of Striding and Springing` (also `Leaping`, as Quick Party spells it), `Boots of Speed`, `Ioun Stone, dusty rose prism`, `Staff of Power`, `Helm of Brilliance`, `Sword +4/+5, Defender`, and any other `Ring of ...` (counts toward the two-ring limit). Rule text is in `WEAR_TEXT` with page numbers; test (f) diffs 63 one-line fragments against the DMG pages.
**Combat page.** Build-up table (no armour 10, suit, magic plus, shield, shield plus, Dexterity, then each item that works) with the page of each rule; items that do not work are listed underneath with the reason and page. `d.ac` everywhere (Simple view, page 1, hit points box, preview) is the build-up total. Saving throws (page 1 and Simple) show the lowered target with the printed figure in brackets.
**The rules, as read, with pages (TB to confirm the starred ones):**
1. Magic armour: each plus is one better than the suit, for any suit (DMG p.164; chain mail +1 is AC 4). Plate Mail of Etherealness is +5 plate, after 5 / 10 / 15 / 20 charges +4 / +3 / +2 / +1 (type `+4` after the name) (DMG p.164-165). Plate Mail of Vulnerability is -2, -3 or -4 plate (type the number; none typed = -2*) (DMG p.165). Only the best suit worn counts.
2. Shield: one better; a magic shield one more per plus, so Shield +1 alone is AC 8 (DMG p.164). Only the best shield counts. Shield, large, +1, +4 vs. missiles: melee AC as +1, and the Combat page shows a second figure against missiles, taking the +4 for the +1 (DMG p.165*). Shield -1, missile attractor: no better than no shield (DMG p.165).
3. Ring of protection: +N AC and +N saves; the 5' radius forms give the wearer the same (the radius bonus is saves only for others, p.130); the table's +4 ring is +4 AC and +2 saves, the +6 ring +6 AC and +1 saves (DMG p.130). No AC from the ring while magic armour is worn (a magic shield is not armour*), but saves still apply. Only the strongest ring of protection works, so two +2 rings are still +2. "Strongest" is taken as most AC, then most saves*. No more than 2 magic rings worn or none function (DMG p.129): any `Ring of ...` counts, so a third worn ring switches all rings off. Two on one hand is not tracked*.
4. Bracers of defense AC N: AC N as if armour and a shield were worn; not effective if any armour is worn (leather included); work with other magical items of protection (DMG p.139). The shield's own 1 is already inside the bracers' figure, so a plain shield adds nothing and a magic shield adds only its plus*. Dexterity adjustment still applies. Bracers of defenselessness are not modelled.
5. Cloak of protection +N: AC N better and +N on saves; it "cannot function" with magic armour, armour other than leather, or any sort of shield, so neither the AC nor the saves count then (DMG p.141). "Leather" is read as the Leather armour item only; padded and studded leather stop it*. It works with bracers, rings and leather armour.
6. Cloak of displacement: after the first attack misses, +2 AC and +2 saves (DMG p.140-141). The automatic first miss is not tracked. Boots of striding and springing +1 AC (p.139). Boots of speed +2 AC only in combat where that movement is possible (p.139): tick Worn when it applies. Dusty rose prism ioun stone +1 protection = 1 better AC (p.147, with "protection" defined as AC at p.140); no save bonus is stated, so none given*. Staff of power +2 AC and saves while wielded (p.134). Helm of brilliance "armor of +2 value" (p.145): read as +2 AC with none of the magic-armour exclusions*. An item of the same kind worn twice counts once*.
7. Sword +4/+5 Defender: each round the wielder may put some, all or none of the plus into AC (p.165): a "held for AC" box on the Equipment row (0 to the plus).
8. Everything above is cumulative with everything else except where a rule above says otherwise (ring p.130: "cumulative with all other magical items of protection except as follows"; cloak p.141 "can be combined with other items").
9. Monks keep the table AC and no Dexterity adjustment (PHB p.30-31); rings, cloaks and the other items add; armour, shields and bracers are ignored.
10. Saves from armour: DMG p.81 says magic armour sometimes adds to saves (against acid except immersion, disintegration, falling, fire, spells that cause physical damage; never gas, poison, spells that do not cause damage; metallic armour not against electrical). That depends on the attack, so it is not added to the five columns: page 1 prints a note with the armour's plus (taken as the bonus, as DMG p.154 and p.158 use it). A bonus on the die is shown as a lower target number, never below 1*.
11. **Weight and movement of magic armour not changed:** the sheet keeps the base suit's weight and speed cap (as the old Quick Party rows did). DMG p.28 says worn magic armour moves at the next higher base rate and weighs half; DMG p.164 says magic armour is virtually weightless with the unarmoured base speed. The two pages disagree, so TB to pick.
**Not modelled (listed so the TD knows):** artifacts and relics (Coat of Arnd p.158 and the artifact power lists p.162, p.167), potion of invulnerability (temporary, p.126), cloak of the manta ray (AC 6 in salt water, p.141), gauntlets of dexterity (they change Dexterity, so the score is edited by hand, p.145), scarab of protection (saves versus magic only, p.154), luck blade and luckstone saves, bracers of defenselessness, plate mail of vulnerability's falling apart on a natural 20, brooch of shielding.
**Wear the best set:** button on the Combat page; also applied to Random PC sheets. It tries every on/off combination of up to 14 wearable items and keeps the lowest AC, then the best saves, then the fewest items.
**Quick Party note for the TD:** `QPRules.calcAC` (the generator's AC, kept in the notes as "Generator armour class") adds a ring of protection and a cloak on top of magic armour and ignores the DMG p.130 and p.141 exclusions, and counts bracers with a shield, so the sheet's AC can be worse than the generator's. Also `Boots of Striding and Leaping` in `TIII` should be "Striding and Springing" (DMG p.139). Both are in `QUICK-PARTY-1e/rules.js`, not edited here.

### Interpretations (TB to confirm)
1. **op bitmask stores the difference from the RAW defaults** (op 0 = all defaults), bits fixed at the section 9 list position (rounds 0, declare 1, surprise 2, surprise-dex 3, surprise-bar 5, initiative 6, phase-order 7). Spec says "bit mask"; this way a toggle added later cannot upset a combat in progress. Section 9 lists 58 toggles, JS bit ops stop at 31: later steps need a second integer for the high ones.
2. **Two sides only**, roster membership stored as `sd[i].m` (roster indexes). Spec 8.2 has no token-to-side field; item `cs` (8.4) is a later step. Tokens added to the scene after Start are not in the roster yet.
3. **Surprise segments (A17, S02, A1)**: round 0 runs segment 1 to N (N = the surprised side's segments after the difference); the other side acts in each. Range 0 means the side cannot be surprised (S04) and needs no roll. Tied surprised rolls cancel (equal = no effect, DMG p.61-62).
4. **S03 DEX**: shown per token in the GM panel for the surprised side (the sheet's DEX, PHB p.11 Table I via `dexReaction`); no sheet = no adjustment. It is display only: the banner is per side. Individuals only matter once attacks exist.
5. **Cm.initiative off** = the GM picks first side (or simultaneous); **cm.phase-order off** = no second-side phase, banner says "any order"; **cm.rounds off** = banner says "Combat" instead of a round number (rounds still count for the log); **cm.surprise-bar off** = the banner does not say the surprised side cannot act; **cm.surprise off** = Start goes straight to round 1.
6. **Log kind 10** (restriction switched) is ours; spec kinds 0 and 1 are used as listed, with `flags` = roll source (0 sheet, 1 typed, 2 tray) and for surprise `need` = the range. Result lines ("Goblins surprised for 1 segment", "Party wins initiative") are kind 0/1 entries with actor -1 and the text field.
7. **Rolling**: the GM rolls for both sides. Source is a setting in the combat state (`rs`), changed mid-combat, recorded per entry. Re-rolling before Next just adds another entry (nothing deleted); the last roll counts.
8. **Dice tray**: reads `rodeo.owlbear.dice/rollValues` from the chosen player's metadata (GM or any player) and takes the first value as the d6. Whether that is an array of numbers or objects, and that it holds only the latest roll, is from the Dice extension notes and the mock only: needs a real room. The tray keeps the last roll, so pressing Read tray twice reads the same die; the GM must roll fresh each time.
9. **Tie note (A23)** is shown as text on a tie; nothing is enforced.
10. **Banner**: popover 340 x 74 at top centre, click-away off, a small x hides it for that player until combat is next started. Opened from `background.js` (SDK popover from a background page) and not testable in the dev mock beyond an iframe stand-in.
